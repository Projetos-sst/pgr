# QA Mapping detalhado — sst-manager

> Mapeamento de QA **ancorado no que foi realmente implementado** (specs `.specs/*` +
> schema + repositórios + domínio + Server Actions + rotas REST + testes de integração/unit
>
> - PRs), e não apenas na intenção das issues. Como houve **mudanças de regra no meio do
>   caminho**, a fonte da verdade aqui é o **código**; as issues dão a visão macro do que era
>   para ser feito. Onde a implementação diverge da issue original, a divergência está marcada
>   com **⚠️ Mudança de regra**.
>
> Objetivo: permitir uma rodada de QA **E2E** precisa, garantindo que cada fluxo respeita as
> regras de negócio efetivamente codificadas.

## Como usar

- Uma seção por **módulo** (agrupando as issues relacionadas). Cada seção tem:
  - **O que foi implementado (código como fonte)** — com referências a arquivos.
  - **Regras de negócio efetivas** — regras/constraints/enums/transições realmente aplicadas.
  - **Casos de teste E2E** — tabela com `ID | Cenário | Pré-condições | Passos | Resultado esperado`.
- **IDs dos casos**: `QA-<sigla>-NN` (ex.: `QA-EMP-01`). Use como referência ao executar/reportar.
- Cada caso cobre, quando aplicável: **happy path**, **isolamento multi-tenant** (org A não
  acessa dado de org B → `NOT_FOUND`/vazio), **autorização** (papel `client` → `FORBIDDEN`),
  **validação** (`VALIDATION`), **duplicidade** (`DUPLICATE`), **FK cross-tenant**
  (`FK_NOT_FOUND`) e edge cases do módulo (saldo insuficiente, token expirado, transição
  inválida, cota, etc.).

## Invariantes globais a checar em TODA seção

1. **Isolamento multi-tenant** — todo acesso passa por `withOrg(orgId)` (fixa
   `app.current_org`) + backstop RLS. O `orgId` vem **sempre da sessão**
   (`requireTenantContext`/`requireOfficeStaff`), nunca de input do cliente. Query sem tenant
   → vazio, nunca vaza entre empresas.
2. **Duas superfícies, um gate** — Server Action (`officeAction` → `ActionResult<T>`) e REST
   `/api/v1` (`restHandler` → HTTP) compartilham repositório, schema Zod e mapeamento de erro.
   Testar ambas quando existirem.
3. **Códigos de erro de domínio** — `VALIDATION`(422), `DUPLICATE`(409), `NOT_FOUND`(404),
   `FK_NOT_FOUND`, `FORBIDDEN`/`NO_TENANT_CONTEXT`(403), `UNAUTHORIZED`(401), além dos
   específicos (`INSUFFICIENT_STOCK`, `ALREADY_SIGNED`, `ALREADY_RETURNED`, `TOKEN_INVALID`,
   `TOKEN_EXPIRED`, `QUOTA_EXCEEDED`, `AI_UNAVAILABLE`, `IN_USE`).

## 1. Fundação — Auth, Tenant e Isolamento (#2 #4 #5 #6 #7)

`Specs:` .specs/001-clerk-auth · .specs/002-drizzle-memberships · .specs/004-multi-tenant-isolation · .specs/005-modelo-tenant-gate-pro
`Migrations:` 0000_initial_schema · 0001_set_updated_at · **0002_app_runtime_role** (role least-privilege + GRANTs) · 0003_numerous_king_bedlam (`tenant_probe` + RLS) · **0004_modelo_tenant_gate_pro** (`orgs.plan` default+CHECK, `companies` + RLS) · 0006_close_data_api_anon_authenticated
`Rotas:` `/` `/sign-in(.*)` `/sign-up(.*)` públicas · demais protegidas por `src/proxy.ts` (Clerk `auth.protect()`); layout `(protected)` como defesa em profundidade · `POST /api/webhooks/clerk` (sync) · `POST /api/webhooks/stripe`
`REST:` gate único via `restHandler` (`src/shared/api/rest.ts`); `/api/me` + `/api/v1/*`. Bypass dev só fora de produção (`APP_ENV!=="production"` && `DEV_API_AUTH_BYPASS==="true"`, headers `x-dev-tenant/role/user`).

### O que foi implementado (código como fonte)

- **Fixação de tenant por transação** — `withOrg(orgId, fn)` (`src/shared/db/with-org.ts`) abre transação e faz `select set_config('app.current_org', orgId, true)` (escopo transação). Todo acesso a dado tenant passa por aqui; o `orgId` vem sempre da sessão.
- **Backstop RLS no banco** — cada tabela tenant tem policy PERMISSIVE `FOR ALL TO app_runtime USING (org_id = current_setting('app.current_org', true)) WITH CHECK (…)` (ver `tenant_probe` em `0003`, `companies` em `0004`). `USING` isola leitura; `WITH CHECK` rejeita escrita cross-tenant. Sem `set_config` → `current_setting(...,true)` retorna vazio → **0 linhas**.
- **Role de runtime least-privilege** — `app_runtime` conecta pelo pooler (porta 6543), **sem BYPASSRLS/superuser** (asseverado em `least-privilege.test.ts`). GRANTs em `users/orgs/org_memberships` (`0002`); escrita em `org_memberships` pelo runtime é bloqueada pela RLS (só policy de SELECT) — a sync do webhook grava por conexão que ignora RLS (`getRlsBypassingSupabaseClient`).
- **Resolução do tenant ativo** — `resolveActiveTenant(userId, cookieTenantId)` (`src/shared/tenant/active-tenant.ts`): lê memberships; 0 → **auto-provisiona** tenant pessoal e relê; 1 → usa o único; ≥2 → escolhe pelo cookie `ACTIVE_ORG_COOKIE` se válido, senão default (org pessoal = `role owner` && `clerkOrgId===null`; fallback determinístico menor `orgId`).
- **Normalização de papéis** — `toDomainRole` mapeia Clerk `org:admin→owner`, `org:member→collaborator`, `org:client→client`; papel **desconhecido → `client`** (menor privilégio). `requireOfficeStaff` admite só `owner`/`collaborator` (`OFFICE_STAFF_ROLES`).
- **Contexto de tenant** — `requireTenantContext()` (`require-tenant-context.ts`): `assertAuthenticated` (senão `UnauthorizedError`) → resolve tenant por cookie → sem tenant lança `NoTenantContextError` + log `blocked`. `requireOfficeStaff()` acrescenta o gate de papel (`ForbiddenError`).
- **Duas superfícies, um gate** — `officeAction(operation, fn, {audit})` (`office-action.ts`) → `ActionResult<T>` (`result.ts`), chama `requireOfficeStaff`, mapeia erro via `toActionError`, audita escrita sem PII, **relança** erro inesperado (não silencia). `restHandler` mapeia os mesmos códigos para HTTP (`HTTP_BY_CODE`).
- **Mapa de erros** — `toActionError` (`action-error.ts`): `ZodError→VALIDATION(422)` com `fields`; `AppError→code próprio`; SQLSTATE via cadeia de `cause` (profundidade 5): `23505→DUPLICATE(409)`, `23503→FK_NOT_FOUND(422)`, `23514/23502→VALIDATION`. Desconhecido → `null` (rethrow / REST 500 `UNKNOWN`).
- **Provisionamento de org pessoal** — `provisionPersonalTenant` (`provision-personal-tenant.ts`): idempotente por busca de owner pessoal (`role owner` && `clerkOrgId null`); cria `orgs` (plan default `free`) + `ensureOwnerMembership` + log `tenant.provisioned`.
- **Sync de webhooks Clerk** — `handleClerkEvent` (`clerk-sync-service.ts`): `user.created`→`replaceUser` + provisiona; `user.updated`→sincroniza **sem** provisionar; `user.deleted`→`deleteUser`; `organization.*`→upsert/replace/delete; `organizationMembership.*`→upsert user+org+membership / delete. Payload inválido (Zod) → `invalid_payload` → **400** sem efeito colateral.
- **Troca de tenant** — `switchTenantAction(orgId)` (`switch-tenant.ts`): valida `orgId` contra memberships do usuário; não-membro → `FORBIDDEN` + log `blocked`, **sem gravar cookie**; membro → grava `ACTIVE_ORG_COOKIE` httpOnly/secure/sameSite=lax + `revalidatePath`.
- **`meAction`** — usa `requireOrgContext()` (org ativa do Clerk, não o modelo de tenant); `NoActiveOrgError→NO_ACTIVE_ORG` (log `access_blocked_no_org`), `UnauthorizedError→UNAUTHORIZED`.
- **Plano free/pro** — `orgs.plan text NOT NULL DEFAULT 'free'` + `CHECK in ('free','pro')` (`0004`). Helpers em `plan.ts`: `isTeamManagementAvailable(plan)` = `pro`; gates de quota por mês (`FREE_SIGNATURE_MONTHLY_QUOTA=10`, `FREE_AI_SUGGESTION_MONTHLY_QUOTA=20`).
- ⚠️ Mudança de regra: coexistem **dois modelos de "org"** — `requireOrgContext`/`meAction` (org ativa do Clerk, specs 001/002) e `requireTenantContext`/`resolveActiveTenant` (Modelo B: escritório = `orgs.id` resolvido de memberships + cookie, specs 004/005). O runtime real usa o segundo; `meAction` é legado da fatia inicial.

### Regras de negócio efetivas

- **Tenant sempre da sessão** — nunca de input do cliente. Alvo de troca é validado contra memberships antes de persistir no cookie.
- **Isolamento em duas camadas** — app (`withOrg`) + banco (RLS `app_runtime`). Query que esquece `withOrg` retorna vazio (não vaza); escrita cross-tenant é rejeitada pelo `WITH CHECK`. O escopo é por transação (não vaza para query bare subsequente).
- **Papéis** — `owner`/`collaborator` = office staff (acesso a Server Actions/REST); `client` e papel desconhecido = menor privilégio, barrados por `requireOfficeStaff`.
- **Plano** — `free` default; `pro` habilita gestão de equipe e quotas ilimitadas; `free` limitado por contagem mensal. `CHECK` no banco recusa plano fora de `{free,pro}`.
- **Provisionamento** — primeiro login (ou `user.created`) sem membership cria tenant pessoal owner automaticamente; idempotente na função (reentrega reprovisiona só se não existir owner pessoal).
- **Webhooks** — sincronizam `users`/`orgs`/`org_memberships`; payload inválido → 400 sem escrever; escrita de membership acontece por conexão que ignora RLS (não pelo `app_runtime`).
- **Códigos por cenário** — anônimo→`UNAUTHORIZED(401)`; sem tenant/org→`NO_TENANT_CONTEXT`/`NO_ACTIVE_ORG(403)`; papel insuficiente→`FORBIDDEN(403)`; duplicidade→`DUPLICATE(409)`; FK→`FK_NOT_FOUND(422)`; inválido→`VALIDATION(422)`.

## 2. Cadastros base — Empresas e Unidades de Obra (#69 #71 #11)

`Specs:` `.specs/006-cadastros-base-pgr` (modelo de dados) · `.specs/007-pgr-base-cruds` (CRUD) ·
`Migrations:` `0005_*` (schema `companies` ALTER + `work_units`, RLS, GRANT, triggers `set_updated_at`) ·
`Rotas UI:` `/companies` (+ `/companies/[id]/edit`), `/work-units` (+ `/work-units/[id]/edit`) ·
`REST:` `/api/v1/companies` (GET/POST), `/api/v1/companies/[id]` (GET/PUT/DELETE), `/api/v1/companies/[id]/dependents` (GET); idem `/api/v1/work-units/**`.

### O que foi implementado (código como fonte)

- **Schema Empresa** — `src/shared/db/schema/companies.ts`: `razao_social NOT NULL`; `cnpj` **nullable**;
  `risk_grade smallint` com `CHECK risk_grade between 1 and 4` (`companies_risk_grade_check`);
  `UNIQUE(org_id, cnpj)` (`uq_companies_org_id_cnpj`); `nome_fantasia`, `phone`, `email`, `cnae`,
  `main_activity`, `logo_path` + colunas de endereço (`addressColumns()`); `org_id → orgs.id ON DELETE cascade`;
  RLS `companies_isolation` (`org_id = current_setting('app.current_org', true)`).
- **Schema Unidade de Obra** — `src/shared/db/schema/work-units.ts`: `company_id uuid NOT NULL → companies.id ON DELETE cascade`;
  `name NOT NULL`, `description NOT NULL` (objeto/descrição), `contract_number` opcional + endereço; RLS `work_units_isolation`.
  ⚠️ **Não há UNIQUE de nome/contrato** — nomes de unidade podem repetir dentro da mesma empresa.
- **Domínio/Zod** — `domains/pgr/companies.ts`: `cnpj` opcional (string vazia → `undefined`, 14 dígitos via `cnpjSchema`);
  `razaoSocial` obrigatória; `riskGrade` **obrigatório**, coagido a número e validado 1–4 (`riskGradeSchema`).
  `domains/pgr/work-units.ts`: `companyId` UUID obrigatório, `name`/`description` obrigatórios, `contractNumber` opcional.
- **Repositórios** — `repositories/companies.ts` / `work-units.ts`: todas as queries em `withOrg(orgId, tx=>…)`;
  paginação offset `{rows,total}` (busca por `razaoSocial`/`cnpj`; unidades por `name`/`contract_number`/`description` + filtro `companyId`);
  escrita via `auditedTenantWrite`. `createWorkUnit`/`updateWorkUnit` chamam `assertCompanyInTenant` → lança
  `ReferenceNotFoundError("company")` (→ **FK_NOT_FOUND**) se a empresa não pertence ao tenant.
- **Dependentes (advisory)** — `countCompanyDependents` conta `work_units`/`ges`/`job_roles`/`employees`;
  `countWorkUnitDependents` conta `ges`. Expostos por `getCompanyDependentsAction` / `getWorkUnitDependentsAction`
  e `GET …/[id]/dependents`. Servem para **aviso de confirmação na UI**, não bloqueiam a exclusão.
- **Actions/REST** — `officeAction(...)` → `ActionResult<T>`; mirror `restHandler(...)` reusa mesmo repo/zod;
  create `201`, delete `204`; `NotFoundError` → 404.

### Regras de negócio efetivas

- **Razão social** obrigatória (NOT NULL no banco + zod). Nome fantasia opcional.
- **CNPJ** opcional; quando informado, normalizado para 14 dígitos. **Único por org** (`UNIQUE(org_id, cnpj)`),
  **não** global → mesmo CNPJ em duas orgs diferentes é aceito; duplicado no mesmo escritório → **DUPLICATE** (SQLSTATE 23505).
- **Grau de risco** obrigatório, inteiro **1–4** (zod + `CHECK` de banco como backstop). Fora do intervalo/ausente → **VALIDATION** (`fields.riskGrade`).
- **Unidade de Obra** exige `companyId`, `name` e `description`. `companyId` deve pertencer ao tenant ativo,
  senão **FK_NOT_FOUND** (validado na app via `assertCompanyInTenant`, antes do insert/update).
- **Isolamento**: tenant sempre da sessão (`requireOfficeStaff`/`withOrg`), nunca do input. Registro de outra org
  em get/update/delete → **NOT_FOUND** (não vaza existência); RLS como backstop.
- **Autorização**: papel `client` → **FORBIDDEN**; só `owner`/`collaborator` (office staff) acessam.
- **Exclusão**: ⚠️ **Mudança de regra vs. expectativa de IN_USE** — a exclusão **não** bloqueia por dependentes.
  `companies` tem `ON DELETE CASCADE` descendo a cadeia (work_units → ges → …) e `work_units → ges` também é CASCADE;
  ou seja, excluir empresa/unidade **remove os filhos em cascata**. O endpoint `dependents` é apenas informativo
  para a UI exibir aviso antes de confirmar — **não existe erro IN_USE neste módulo**.
- **Endereço**: modelo tem colunas de endereço tanto em empresa quanto em unidade; a UI de unidade pode
  pré-preencher copiando o endereço da empresa (`listCompanyOptions` retorna os campos de endereço), mas isso é
  conveniência de formulário — o valor persistido é o enviado no payload da unidade.

`REST:` `/api/v1/ges` (GET/POST) · `/api/v1/ges/[id]` (GET/PUT/DELETE) · `/api/v1/ges/[id]/dependents` (GET) · `/api/v1/ges/[id]/job-roles` (GET list, `?available=true` → funções disponíveis; POST vincula) · `/api/v1/ges/[id]/job-roles/[linkId]` (PUT/DELETE) · `/api/v1/job-roles` (GET/POST) · `/api/v1/job-roles/[id]` (GET/PUT/DELETE) · `/api/v1/job-roles/[id]/dependents` (GET) · `/api/v1/employees` (GET/POST) · `/api/v1/employees/[id]` (GET/PUT/DELETE) · `/api/v1/employees/[id]/epi-record` (GET, ficha EPI read-only)

### O que foi implementado (código como fonte)

- **GES** (`ges`): pertence a `company_id` + `work_unit_id` (ambos NOT NULL, tenant-scoped). Ao criar/editar, `assertWorkUnitInCompany` valida que a unidade pertence à empresa e ao tenant → senão `FK_NOT_FOUND` (`ReferenceNotFoundError("work_unit")`). Lista traz **nº de expostos derivado** por `coalesce(sum(worker_count),0)` do join com `ges_job_roles` + `totalWorkers` agregado da página. `getGesAction` devolve `{ges, exposedWorkers}` recontado.
- **Funções/Cargos** (`job_roles`): pertence a `company_id`. `assertCompanyInTenant` valida empresa no tenant → `FK_NOT_FOUND` (`"company"`). Busca por `title`/`cbo` (ilike), filtro por `companyId`, paginação offset (`{rows,total}`).
- **Vínculo Função↔GES** (`ges_job_roles`): `createGesJobRole` carrega `companyId` do GES (`loadGesCompanyId` → `FK_NOT_FOUND "ges"`), depois `assertJobRoleInCompany` garante que a função é da MESMA empresa do GES → senão `FK_NOT_FOUND "job_role"`. `workerCount` re-validado por `workerCountSchema` (int>0). `listAvailableJobRolesForGes` lista funções da empresa do GES **ainda não vinculadas** (`notInArray`). `updateGesJobRole` é parcial: `workSchedule` ausente PRESERVA o valor (não apaga).
- **Funcionários** (`employees`): `company_id` NOT NULL; `ges_id`/`job_role_id` nullable. `assertReferences`: empresa no tenant (`FK_NOT_FOUND "company"`); se `gesId`, GES deve ser da mesma empresa (`"ges"`); se `jobRoleId`, exige `gesId` E existência do vínculo `(ges,jobRole)` em `ges_job_roles` (`"job_role"`) — **função do funcionário tem de ser uma das vinculadas ao GES**. CPF via `cpfSchema` (11 dígitos, só dígitos). Enums opcionais (`sex`/`maritalStatus`/`status`), `status` default `active`. Lista faz join p/ `companyName`/`gesName`, busca por nome/ges/função, filtro `companyId`/`status`.
- **Gate**: todas as Server Actions via `officeAction(...)` (`requireOfficeStaff` → só `owner`/`collaborator`); REST via `restHandler`. Escritas com `audit:true`/`auditedTenantWrite`.

### Regras de negócio efetivas

- **Nº de expostos por GES = DERIVADO** (`SUM(worker_count)` de `ges_job_roles`; **0 sem vínculos**; sem coluna nem trigger — recalculado a cada leitura/lista).
- **`worker_count > 0`** (CHECK `ges_job_roles_worker_count_check` + `workerCountSchema` int positivo).
- **Único `(org_id, ges_id, job_role_id)`** (`uq_ges_job_roles_org_ges_role`) → vínculo duplicado = `DUPLICATE` (23505).
- **CPF único por tenant**: `uq_employees_org_cpf (org_id, cpf)` → `DUPLICATE`. **CPF NÃO é único global** (mesmo CPF permitido em orgs diferentes).
- **Único `(org, company, title)`** em `job_roles` (`uq_job_roles_org_company_title`) → título duplicado na empresa = `DUPLICATE`.
- **Enums fechados**: sexo `male|female|not_informed`; estado civil `single|married|divorced|widowed|stable_union`; status `active|on_leave|dismissed` — valor fora → `VALIDATION`.
- **Função filtrada pelas do GES**: no cadastro de funcionário, `jobRoleId` só aceito se existir vínculo `(gesId, jobRoleId)`; `jobRoleId` sem `gesId` → `FK_NOT_FOUND`. Funções "disponíveis" para vincular = da empresa do GES e não vinculadas.
- **Coerência empresa**: GES→work_unit, job_role e vínculo devem compartilhar a empresa; cross-company/cross-tenant → `FK_NOT_FOUND`.
- **ON DELETE**: `companies→work_units→ges→ges_job_roles` e `job_roles→ges_job_roles` = **CASCADE**; `employees.ges_id`/`job_role_id` = **SET NULL**. Deletar GES/função **não bloqueia** (sem `IN_USE`): cascateia vínculos e zera FKs de funcionários. Endpoint `dependents` é **informativo** (conta `jobRoleLinks`/`employees`), não impede a exclusão.
- **Isolamento**: `withOrg` + RLS `app_runtime`; tenant sempre da sessão. Sem tenant → gate bloqueia; repo/RLS nunca vazam entre orgs.

### O que foi implementado (código como fonte)

- **Categorias** (`categories.ts` schema/repo/domain/action + `api/v1/categories/**`): CRUD completo. Enum `category_type` (`epi|machine`). `UNIQUE(org_id,type,name)` = `uq_categories_org_type_name` → duplicidade `DUPLICATE` (23505). `UNIQUE(id,type)` = alvo da FK composta do catálogo. Delete sem helper de dependentes (repo `deleteCategory` faz DELETE direto).
- **Catálogo EPI** (`epis.ts`/`epi-catalog.ts`): CRUD via Server Actions (`officeAction`). FK composta `(category_id,type)→categories(id,type)` ON DELETE RESTRICT garante item.type == categoria.type. `assertCategoryInTenant` (sob `withOrg`) valida categoria no tenant + tipo → `ReferenceNotFoundError` (FK_NOT_FOUND) em cross-tenant/tipo divergente/inexistente. Sem unicidade de nome. Delete atômico: `FOR UPDATE` → conta dependentes (`epi_stock`, `epi_risk`, `epi_delivery_items`) → `EntityInUseError` (IN_USE 409) se houver; backstop FK 23503→IN_USE. `countEpiCatalogDependents` para aviso na UI.
- **Estoque** (`epi-stock.ts`): CRUD; `balance` **read-only** (default 0, nunca no create/update — só movimentações alteram). Create define só `minimumQuantity` (`epiMinQuantitySchema`, ≥0); update edita só a mínima. `UNIQUE(org_id,catalog_id)`. Status **derivado** (`deriveStockStatus` + `statusFilter` SQL): `sem_saldo` (≤0), `abaixo_minima` (0<bal<min), `acima_minima` (bal≥min). `listAvailableCatalogOptions` = itens do catálogo ainda sem estoque (`notInArray`). `countEpiStockDependents` = nº de movimentos removidos em CASCADE.
- **Movimentações** (`stock-movements.ts`): `quantity>0` (CHECK + zod); sinal pelo `type` — `purchase`/`employee_return` somam, `adjustment`/`discard`/`employee_delivery` subtraem (`signedQuantity`, `ENTRY_TYPES`). Saída manual só `{adjustment,discard}` (`stockExitTypeSchema`). Escrita transacional: `lockStockRow` (`SELECT … FOR UPDATE`) → valida `novoSaldo≥0` (senão `InsufficientStockError` → INSUFFICIENT_STOCK 422 + rollback total) → INSERT movimento + UPDATE `epi_stock.balance`. `CHECK balance>=0` = backstop de corrida. Histórico paginado (`movement_date DESC, created_at DESC`) com **saldo resultante derivado** por window function (`sum(...) over (order by ... asc)`, espelha `computeRunningBalance`); LEFT JOIN traz `employeeName` só em movimento de entrega.

### Regras de negócio efetivas

- Categoria única por `(org,type,name)`; `type ∈ {epi,machine}`.
- Catálogo: coerência categoria×type garantida no banco (FK composta) + app (`assertCategoryInTenant`); tipo divergente/categoria de outro tenant → FK_NOT_FOUND.
- `epi_stock.balance` imutável pelo CRUD; alterado exclusivamente por movimentações via transação atômica.
- Status de estoque derivado na leitura (sem coluna/trigger).
- Movimento `quantity>0`; sinal pelo tipo; saída nunca deixa saldo negativo (INSUFFICIENT_STOCK + rollback); histórico com saldo acumulado derivado (window fn, correto mesmo paginando).
- Delete de catálogo em uso → IN_USE (409). Delete de categoria referenciada por catálogo → FK RESTRICT → 23503 → **FK_NOT_FOUND (422)** (categorias não têm guarda de dependentes; a barreira é a FK do banco).
- Isolamento por `withOrg` + RLS; tenant sempre da sessão. Cross-tenant → NOT_FOUND (repo filtra por `org_id`). Papel `client` → FORBIDDEN (`requireOfficeStaff`).

## 5. EPI — Entrega, Devolução, Ficha e Assinatura Digital (#19 #20 #21 #67)

`Specs:` `.specs/010-digital-signature-infra/`, `.specs/012-epi-module-completion/` ·
`Migrations:` `0010_digital_signature_infra` (infra genérica: `signature_requests`/`signature_captures` + policies) · `0011_epi_delivery_return` (`employee_return` no enum + `returned_at` em `epi_delivery_items`) ·
`Rotas UI:` `/employees/[id]` (entrega/assinatura/devolução/ficha via `_components/delivery-signature.tsx`), `/epi-stock`, `/signatures` (infra 010) ·
`REST:` `GET|POST /api/v1/epi-deliveries`, `GET|DELETE /api/v1/epi-deliveries/[id]`, `POST /api/v1/epi-deliveries/[id]/sign` (assinatura manual), `POST /api/v1/epi-deliveries/[id]/return` ·
`Rota pública:` `/sign/[token]` (EPI inline, 012) · `/signature-requests/[token]` (infra genérica, 010). Ambas em `src/app/(public)/`, sem sessão.

### O que foi implementado (código como fonte)

**⚠️ Existem DOIS mecanismos de assinatura distintos — não confundir:**

**(A) Assinatura de EPI INLINE (fatia 012)** — `epi_deliveries.auth_token` + `signature_status` (enum `pending|signed_qr|signed_link|signed_manual`). É a que serve a entrega de EPI.

- Token **stateless HMAC** (`src/shared/integrations/epi-signature/token.ts`): `base64url(payload).base64url(HMAC_SHA256(payload, EPI_SIGN_TOKEN_SECRET))`. Payload embute `orgId`, `deliveryId`, `method` (qr|link, escolhido pelo técnico) e `iat`. TTL 72h validado na app (`SIGN_TOKEN_TTL_MS`).
- **⚠️ Mudança de regra vs. a regra genérica do card:** o token de EPI **NÃO é hasheado nem armazena token_hash**. O token cru é gravado direto em `epi_deliveries.auth_token` (um token ativo por entrega; regenerar substitui). O isolamento vem do **payload HMAC-assinado** (`orgId` → `withOrg`), não de policy de capability. `auth_token` é **limpo na transição de assinatura** (`set authToken=null`) — invalida o link (uso único derivado do `signature_status != 'pending'`).
- Repos (`db/repositories/epi-deliveries.ts`): `createDelivery` (baixa transacional), `signDeliveryManual`, `generateSignToken`, `getDeliveryByToken` (leitura pública), `signByToken` (confirmação pública), `returnDeliveryItem` (devolução por item), `deleteDelivery` (só `pending`).
- Actions (`server/actions/pgr/epi-deliveries.ts`): CRUD + `generateSignTokenAction` (office, gera URL+QR, **sem espelho REST** — token é credencial de escrita), `getDeliveryByTokenAction`/`submitSignatureAction` (públicas, sem `requireOfficeStaff`, erro vira `ActionResult`, nunca 500).
- Verificação do token (`verifyToken`): HMAC em tempo constante **antes** de olhar conteúdo → malformado/adulterado/inexistente = mesmo `TokenInvalidError` (anti-enumeração); só token autêntico chega a `TokenExpiredError`.

**(B) Infra de Assinatura Digital GENÉRICA (fatia 010)** — `signature_requests` + `signature_captures`, polimórfica por `target_type` (registry). Usada por PGR/OS/demo etc., NÃO pela entrega de EPI.

- Token **hasheado** sha-256 em `token_hash` (`domains/signatures/token.ts`); cru só na URL/QR. RLS por **capability** (`token_hash = current_setting('app.signature_token')`) via `withSignatureToken`. Uso único por `used_at` (UPDATE atômico `WHERE used_at IS NULL` em `consumeAndCapture`). Captura = imagem base64 PNG em `signature_captures`.
- Quota: `createSignatureRequestCore` → `countRequestsInCurrentMonth` + `isSignatureAvailable(plan,count)`; `free` = **10/mês** (`FREE_SIGNATURE_MONTHLY_QUOTA`), `pro` ilimitado → `QuotaExceededError` (REST 402). Gate só na **criação**; rota pública nunca checa plano.
- Público (`actions/public-signatures.ts`): `resolvePublicSignature` → estado `signable|invalid|expired|used`; `submitPublicSignature` → `fail("NOT_FOUND"|"ALREADY_USED"|"EXPIRED")`. "Expirado" é **derivado** (`isExpired`: `status='pending' && expires_at < now`), nunca persistido.

**Ficha por funcionário (US5)** — `getEmployeeEpiRecord` (`db/repositories/employee-epi-record.ts`): read model **read-only** (join `epi_deliveries × epi_delivery_items × epi_catalog`), `withOrg` + filtro por `employeeId`, filtros `status`(devolvido/em uso)/`from`/`to`, paginação offset. Funcionário inexistente/cross-tenant → `NotFoundError`.

### Regras de negócio efetivas

- **Entrega baixa estoque transacional** (`createDelivery`): 1 transação `withOrg` — insere entrega `pending`; por item `SELECT epi_stock … FOR UPDATE` (deriva `catalogId`), insere item, `applyStockExit` (`employee_delivery`). `CHECK balance >= 0` + validação na app → saldo insuficiente lança `INSUFFICIENT_STOCK` (422) e faz **rollback total** (nada persiste, nenhum saldo muda).
- **Token EPI**: único por entrega (índice parcial `uq_epi_deliveries_auth_token WHERE auth_token is not null`), **não hasheado**, TTL 72h (`iat` no payload), uso único via limpeza de `auth_token` + guard `signature_status='pending'` no UPDATE condicional. Isolamento vem do `orgId` assinado no token.
- **Assinatura pública** (`signByToken`): `verifyToken` → `withOrg(payload.orgId)` → UPDATE `pending → signed_qr|signed_link` (método vem do payload ASSINADO, cliente não escolhe) exigindo `auth_token = token AND signature_status='pending'`, limpando `auth_token`. Já assinada → `AlreadySignedError` (409, mensagem amigável). Token inválido → `TokenInvalidError` (404); expirado → `TokenExpiredError` (410).
- **Assinatura manual** (`signDeliveryManual`): UPDATE one-shot atômico `pending → signed_manual`; corrida deixa só uma passar; já assinada → `ALREADY_SIGNED`.
- **Devolução** (`returnDeliveryItem`): trava item `FOR UPDATE`, guard `returned_at IS NULL` (senão `ALREADY_RETURNED` 409), seta `returned_at=now()` e repõe saldo via `applyStockEntry`(`employee_return`). Independe do status de assinatura; rollback total em falha. (Há também `recordReturn` em `epi-returns.ts` para devolução em lote por entrega assinada.)
- **Entrega assinada é imutável**: `deleteDelivery` só apaga `pending` (senão `ForbiddenError`); saldo só volta por devolução.
- **Quota (infra 010)**: free 10 signature_requests/mês → `QUOTA_EXCEEDED` (402), só na criação.
- **Expiração DERIVADA na leitura** nos dois sistemas (não há status `expired` persistido).

## 6. Integrações externas — CAEPI, ViaCEP, CNPJ (#75 #115 #68)

`Specs:` `.specs/011-caepi-ca-validation/`, `.specs/012-epi-module-completion/` (wiring do `CaField` no `epi-catalog-form.tsx`) · `Migrations:` `0008_epi_catalog_type_fk`, `0009_caepi_certificates` (tabela GLOBAL, sem `org_id`/RLS de tenant; RLS habilitado com policy única de leitura global `USING (true)`; `app_runtime` = SELECT-only, escrita só via owner/unpooled pelo job) · `Rotas UI:` autofill inline via `CaField` (CAEPI) e hooks `use-cep-lookup`/`use-cnpj-lookup` nos formulários de empresa · `REST:` `GET /api/integrations/caepi/[ca]` · `GET /api/integrations/cep/[cep]` · `GET /api/integrations/cnpj/[cnpj]` (surface de integração, session-guarded por `requireAuth()`, dados públicos, SEM tenant/papel).

### O que foi implementado (código como fonte)

- **CAEPI (consulta 100% local)**: `lookupCaRecord` (`src/shared/integrations/caepi/lookup.ts`) → `getByCa` (`repositories/caepi.ts`, 1 SELECT por PK, sem `withOrg`) → `validateCa` (`caepi/validate-ca.ts`). Nunca lança; todo desfecho é um estado do contrato `CaLookupResult` (`caepi/types.ts`): união fechada `valid | expired | not_found`, sempre **payload 200**.
- **Normalização de CA** (`caepi/normalize.ts`): `normalizeCa` = só dígitos (sem strip de zeros à esquerda); `isValidCa` = 1–10 dígitos e sem letras no original.
- **Regra de vigência** (`validate-ca.ts`, pura): `valid` ⇔ situação normalizada (uppercase + NFD sem acento) `= "VALIDO"` **E** `validUntil >= today` (comparação lexicográfica `YYYY-MM-DD`, inclusivo). Qualquer outra combinação — inclusive situação desconhecida — é `expired` (conservador). `today` = `todayInSaoPaulo()` (fuso `America/Sao_Paulo`, `src/shared/dates.ts`).
- **`not_found`**: quando a base tem a linha ausente; `getByCa` faz segunda query "existe alguma linha?" e, se base vazia, o lookup anexa `baseUnsynced: true` (distingue "CA não existe" de "base CAEPI nunca sincronizada").
- **Rota CAEPI** (`app/api/integrations/caepi/[ca]/route.ts`): `ensureSession()` → `isValidCa` (senão `invalidFormat` 422) → `lookupCaRecord(normalizeCa(ca))` → `NextResponse.json(ok(result), {status:200, "Cache-Control":"no-store"})` (sem cache: resposta depende de "hoje").
- **Ingestão CAEPI** (`scripts/caepi-sync.ts` + `caepi/parse.ts` + `repositories/caepi-upsert.ts`): job Playwright/CSV, upsert idempotente por `ca` (`ON CONFLICT`), handle owner injetado, fora do escopo desta consulta de leitura (é escrita administrativa).
- **ViaCEP** (`providers/viacep.ts` + `cep.ts`): `lookupCep` com `TtlCache` (~30 dias) de sucesso. Traduz falha em `ProviderResult`: 400/404 → `not_found`; `{erro:true|"true"}` → `not_found`; status ≠200 → `upstream_error`; payload inválido → `invalid_payload`.
- **CNPJ/BrasilAPI** (`providers/brasilapi.ts` + `cnpj.ts`): `lookupCnpj` com `TtlCache` (~7 dias). 404 → `not_found`; mesma tradução de falhas. UA identificável no `http.ts` (Cloudflare barra UA padrão).
- **Validação CEP/CNPJ** (`validation.ts`, pura): `isValidCep` = exatamente 8 dígitos; `isValidCnpj` = 14 dígitos + DV módulo-11, rejeita sequências repetidas (`00000000000000`).
- **Rotas CEP/CNPJ**: `ensureSession()` → validação de formato (senão 422) → provider → `respondWithProviderResult`: `ok`→200 cacheável (`public, max-age=86400, s-maxage=604800`); `not_found`→404; timeout/erro/payload→**502** (`UPSTREAM_ERROR`, silencioso).
- **`ensureSession`** (`_lib/respond.ts`): `requireAuth()`; sem sessão → 401 (`UNAUTHORIZED`). Não exige tenant nem papel.
- **HTTP** (`providers/http.ts`): `fetch` com timeout 5s via `AbortController`; `AbortError`→`timeout`; qualquer exceção→`upstream_error`. Falha externa nunca vira exceção que atravessa a camada.
- **Hooks client**: `useCaepiValidation` (wrapper de `useLookup`): dispara só com formato válido, aborta requisição anterior, nunca lança; deriva status do payload; `onFound` chamado em `valid` **E** `expired` (autofill nos dois), nunca em `not_found`. `CaField` faz autofill fabricante/norma/validade e **nunca bloqueia** o cadastro.

### Regras de negócio efetivas

- `CaLookupResult` `valid`/`expired`/`not_found` como **payload 200**; regra de vigência: `valid` ⇔ situação `VALIDO` **E** `valid_until ≥ hoje` (fuso `America/Sao_Paulo`, inclusivo — `== hoje` é `valid`); situação desconhecida → `expired`; base vazia → `not_found` (+`baseUnsynced`); **NUNCA bloqueia cadastro**; autofill fabricante/norma/validade também em `expired`.
- CAEPI é **SELECT-only** para o runtime (`app_runtime`); escrita só via owner (job de ingestão).
- ViaCEP/CNPJ: autofill com **fallback gracioso** — timeout/erro/payload → 502 silencioso, `not_found` → 404, UI não bloqueia o cadastro.
- Todas as rotas de integração exigem **sessão** (`requireAuth`), mas não tenant/papel (dados públicos).

### O que foi implementado (código como fonte)

- **PGR (documento)** — `schema/pgr.ts` + `repositories/pgr.ts` + `actions/pgr/pgr.ts` + `api/v1/pgr/**`. CRUD completo dual-surface. FK `company_id → companies` (NOT NULL, ON DELETE CASCADE) e `work_unit_id → work_units` (nullable, ON DELETE SET NULL). Isolamento por `withOrg` + RLS `pgr_isolation`. `createPgr`/`updatePgr` fazem `assertCompanyInTenant` e, se houver obra, `assertWorkUnitInCompany` (obra tem de pertencer à empresa informada **e** ao tenant) → `ReferenceNotFoundError` = `FK_NOT_FOUND`.
- **Enum `pgr_registration_type`** = `crm|crea|mte|not_applicable` (default `not_applicable`). Aceite da Declaração de Ciência de Riscos (NR-01): `pgrCreateSchema` exige `declarationAccepted: literal(true)` como **gate de servidor**; **não é persistido** (a action remove antes do repo — a tabela não tem coluna).
- **Risco (inventário do GES)** — `schema/risks.ts` + `repositories/risks.ts` + `actions/pgr/risks.ts` + `api/v1/risks/**`. CRUD completo. FK `ges_id → ges` (NOT NULL, CASCADE); `createRisk`/`updateRisk` fazem `assertGesInTenant` → `FK_NOT_FOUND`. Campos NR-01/eSocial S-2240 (`agent_type`, `hazard`, `description`\*, `sources`, `propagation`, `exposure_time`, `possible_injuries`, `noxious_agent_code`, `measurement_unit`, `concentration_intensity`). `agent_type` e `description` obrigatórios.
- **Enums de risco**: `risk_agent_type` (7 grupos: physical/chemical/biological/ergonomic/mechanical/accident/psychosocial); `exposure_time` (8 faixas); `measurement_unit` (10, `qualitative_na` p/ qualitativo); `assessment_criterion` (qualitative/quantitative); `control_level` (4 níveis NR-01: elimination/collective_protection/administrative/ppe).
- **Avaliação 5×5** (`risk_assessments`): CHECKs `probability between 1 and 5`, `severity between 1 and 5`, `risk_level between 1 and 25`, **coerência `risk_level = probability * severity`**, `uncertainty_degree between 0 and 2`. `risk_level` é persistido pela aplicação. (⚠️ Nota vs. task: a matriz é **1–5** / 1–25, não "1–5" simples — sev/prob 1–5, produto 1–25.)
- **Medidas de controle** (`control_measures`): 1 linha por (risco × nível), `unique(org_id, risk_id, control_level)`, `applicable` + justificativa/monitoramento + plano 5W2H.
- **EPI×Risco** (#78/#22) — `schema/epis.ts` (`epi_risk`) + `domains/pgr/epi-risk.ts` + `repositories/epi-risk.ts` + `actions/pgr/epi-risk.ts` + `api/v1/risks/[id]/epis/**`. Vínculo item do catálogo (`catalog_id → epi_catalog`) × risco (`risk_id → risks`), `unique(org_id, catalog_id, risk_id)` → duplicado = `DUPLICATE`. `neutralization` enum **3 estados**: `neutralizes` ("Sim") / `does_not_neutralize` ("Não") / `not_applicable` ("Não Aplicável"). `createRiskEpi` faz `assertRiskInTenant` + `assertCatalogInTenant` (ambos sob `withOrg`, barreira real de isolamento contra a FK que ignora RLS). `listAvailableEpisForRisk` filtra `type='epi'` do tenant **não** já vinculados, busca por nome/CA. Update só troca `neutralization`; delete é físico. `null`/`false` ⇒ `NOT_FOUND`.

- **⚠️ Mudança de regra — "reutilização copia só riscos do próprio escritório":** NÃO há cópia server-side. Reutilização é **prefill de UI** (`/risks/new?from=<id>`, FR-011/US3 da spec 014): a origem é lida por `getRiskById` (tenant-scoped) e os campos são copiados no formulário; a criação segue o `createRisk` normal. O "só do próprio escritório" é garantido implicitamente — um risco de outro tenant retorna `NOT_FOUND` no `getRiskById` e não pode ser pré-preenchido. Nenhum endpoint/repo de copy/clone existe.
- **⚠️ Nota — neutralização "N.A." vs. "risco sem EPI":** `not_applicable` é um vínculo EPI×risco existente cuja neutralização não se aplica (EPI listado, ex. risco ergonômico). "Risco sem EPI" = **ausência de vínculo** (nenhuma linha em `epi_risk`). São estados distintos — não confundir.

### Regras de negócio efetivas

- PGR vinculado a company (obrigatória) e work_unit (opcional) **do mesmo tenant**; obra tem de pertencer à empresa informada. `registration_type` enum de 4 valores; número de registro **obrigatório** p/ crm/crea/mte e **proibido** p/ not_applicable (refine zod). Validade não pode ser anterior à emissão. Aceite da declaração NR-01 obrigatório na criação (não persistido).
- Risco vinculado a **GES do tenant**; `agent_type`+`description` obrigatórios. Regra `qualitative_na`: `concentration_intensity` só é permitida com `measurement_unit` **quantitativa** (unidade ausente ou `qualitative_na` + concentração → VALIDATION).
- Avaliação: prob/sev 1–5, `risk_level = prob × sev` (1–25) com CHECK de coerência; grau de incerteza 0–2. Controle: 4 níveis NR-01, único por (risco, nível).
- Vínculo EPI×risco: EPI e risco do mesmo tenant; único por (org, catálogo, risco); neutralização `neutralizes`/`does_not_neutralize`/`not_applicable` (Sim/Não/N.A.), obrigatória. N.A. NÃO significa "sem EPI" (esse é ausência de vínculo).
- Reutilização = prefill de formulário (copia campos exceto `id`), **restrita ao próprio escritório** por o `getRiskById` de origem ser tenant-scoped (não há cópia no servidor).
- Autorização: `officeAction`/`restHandler` → `requireOfficeStaff()` (só `owner`/`collaborator`; `client` → `FORBIDDEN`). Tenant sempre da sessão.

## 8. PGR — Metodologia, Avaliação e Sugestão por IA (#76 #25 #77)

`REST:`

- `GET|POST /api/v1/risks/[id]/assessments` — lista (paginada) / cria (`201`).
- `GET|PUT|DELETE /api/v1/risk-assessments/[id]` — `204` no delete.

- `POST /api/v1/ges/[id]/risk-suggestions/accept` — persiste rascunhos (`201`, `{created}`).

### O que foi implementado (código como fonte)

**Metodologia (#76).** `risk_methodology` = **uma linha por org** (`unique("uq_risk_methodology_org")` = alvo do upsert). Base (`aiha|as_nzs_4360|fundacentro|custom`) + gradações de probabilidade/severidade e faixas de classificação em JSONB (validados por Zod em `methodology.ts`). Regras Zod: exatamente **5 gradações** por eixo, `level` em ordem 1..5; exatamente **5 faixas** na ordem canônica `trivial→tolerable→moderate→substantial→intolerable`, `maxLevel` estritamente crescente, última fecha em **25** (particiona [1,25] sem lacuna). Leitura via `getRiskMethodologyView`: se não há linha, devolve o **padrão derivado** (`configured:false`, `defaultRiskMethodology()`) **sem persistir**. `classify(level, bands)` (puro) mapeia nível→classe; `buildMatrix` deriva as 25 células (matriz não é gravada célula a célula). Upsert por `officeAction`+`auditedTenantWrite`.

**Avaliação (#25).** `risk_assessments` (migration 0012). Input Zod (`risk-assessment.ts`): `criterion` (`qualitative|quantitative`), `probability` 1–5, `severity` 1–5, `uncertaintyDegree` 0–2 (default 0, coerção string→número), `toleranceLimit?`, `assessedAt` (AAAA-MM-DD). **`risk_level` e `result` NÃO entram no input** — derivados no servidor por `deriveAssessmentResult`: `riskLevel = computeRiskLevel(prob, sev)` (= prob×sev) e `result = classify(riskLevel, classificationBands)` da metodologia da org (snapshot do momento). Repo valida `assertRiskInTenant` (risco fora do tenant → `ReferenceNotFoundError`/FK_NOT_FOUND). Histórico ordenado por `assessedAt desc, createdAt desc`.

**Sugestão por IA (#77).** Núcleo `server/pgr/ai-risk-suggestion-core.ts` compartilhado por Server Action e REST. `runSuggestRisks`: (1) `fetchGesRiskContext` — contexto **não-PII** do GES (processo/ambiente + **títulos** de função e `workerCount`, **nunca `employees`**); GES de outra org → invisível pela RLS → `null` → `ReferenceNotFoundError`/**FK_NOT_FOUND antes do LLM**; (2) cota `countAiUsageInCurrentMonth(AI_RISK_SUGGESTION_KIND)` checada **antes** da chamada externa; `!isAiSuggestionAvailable(plan, used)` → `QuotaExceededError` (free 20/mês, pro ilimitado); (3) só então `requestRiskSuggestions` (Anthropic via **tool use**, saída validada por Zod `parseModelSuggestions` item-a-item, ≤`MAX_SUGGESTIONS=12`, lista vazia é válida); (4) `recordAiUsage` append-only. Nos testes o cliente Anthropic é **mockado** (`ANTHROPIC_BASE_URL`).

### Regras de negócio efetivas

- **Uma metodologia por org** (`unique(org_id)`); leitura devolve padrão derivado quando não configurada (não grava fantasma).
- Gradações **1–5** (5 por eixo, em ordem); faixas de classificação cobrem [1,25] contíguo, última fecha em 25.
- `nivel_risco = prob × sev` **calculado e persistido no servidor**; classificação (`result`) via faixas da org, snapshot no momento.
- CHECKs no banco: prob 1–5, sev 1–5, risk_level 1–25, `risk_level = prob*sev`, uncertainty 0–2.
- IA: contexto **sem PII** (só GES + títulos de função), chave **server-only**; **isolamento e cota checados ANTES do LLM** (GES cross-tenant → FK_NOT_FOUND sem chamar); saída estruturada validada por Zod vira **rascunho** em `risks`; cota **free 20/mês**; falha do LLM → **AI_UNAVAILABLE (502)**.
- Gate `requireOfficeStaff` em todas as superfícies (papel `client` → FORBIDDEN); RLS backstop + `withOrg` em todo acesso.

### O que foi implementado (código como fonte)

**Plano de ação / medidas de controle (#26, fatia 018)** — CRUD por risco.

- Domínio `domains/pgr/control-measure.ts`: `controlMeasureInputSchema` (5W2H: `controlLevel`, `applicable`, `justification`, `monitoring`, `actionWhat/How/Tracking/Measurement/Responsible/Deadline`). `applicable` via `preprocess` explícito (aceita boolean do REST e string de form; só `true/on/1/yes` → true). `superRefine`: se `applicable=true`, `actionWhat` e `actionHow` são obrigatórios (senão `VALIDATION`).

- `control_level` é **imutável** no update (`toWriteColumns` não inclui `control_level`/`risk_id`); UNIQUE `(org_id, risk_id, control_level)` → `DUPLICATE`/409 ao repetir nível.

Escritas via `auditedTenantWrite`. Ordenação fixa NR-01 (`elimination→collective_protection→administrative→ppe`). Lista paginada `{rows,total}`.
- Actions `actions/pgr/control-measures.ts` (`officeAction`, `audit:true` nas escritas): list/get/create/update/delete → `NotFoundError` quando id não existe/cross-tenant.

**Visão consolidada (#27, fatia 019)** — read-only, `GET /api/v1/pgr/[id]/consolidated`.

- Domínio `domains/pgr/pgr-consolidated.ts`: estrutura **derivada** PGR → GES vinculados → riscos (detalhe + eSocial S-2240) → avaliação vigente (última por `assessed_at`/`created_at`) → medidas 5W2H (estado derivado) → **EPIs por risco**. Sem migration.
- `sortConsolidatedRisks`: riscos **com** avaliação primeiro por `riskLevel` desc (desempate estável por descrição); **sem** avaliação por último.
- Repo `pgr-consolidated.ts` faz joins profundos, todos escopados por `org_id` sob `withOrg`. PGR inexistente/cross-tenant → `NOT_FOUND`/404.

**PGR ↔ GES (#27, fatia 019/022)** — `domains/pgr/pgr-ges.ts` input só `gesId` (pgrId da rota, orgId da sessão). UNIQUE `(org_id, pgr_id, ges_id)` → `DUPLICATE`/409. UNIQUE `(org_id, pgr_id, revision_number)` = backstop → `DUPLICATE`/409. REST create = 201.

**Assinatura pública do PGR (#79, fatia 022)** — reusa infra genérica (`target_type:'pgr'`).

- Núcleo `server/pgr/pgr-signature-core.ts`: valida PGR no tenant (`getPgrSignatureSource`) → **404 antes de cota/escrita** se inexistente/cross-tenant; monta payload público mínimo **no servidor** (título via `buildPgrDocumentTitle`, dados do PGR + `revisionNumber` atual). Delega ao `createSignatureRequestCore`.
- `createSignatureRequestCore`: **gate de cota por tenant/mês** (`countRequestsInCurrentMonth`, sem filtro de `target_type`; `free` = `FREE_SIGNATURE_MONTHLY_QUOTA=10`, `pro` ilimitado → `QuotaExceededError` = `QUOTA_EXCEEDED`/402). Gera token de alta entropia, persiste **só o hash**, monta `publicUrl`+QR. `publicUrl`/token cru **só** existem na resposta de criação — nunca logados/persistidos/retornados no GET.
- `getPgrSignatureView`: estado **derivado** (`none|pending|signed|expired|cancelled`); `expired` derivado por `isExpired(expiresAt,status)`; **nunca** devolve token/URL.
- Superfície pública `actions/public-signatures.ts` (`submitPublicSignature`/`resolvePublicSignature`): **sem** gate office staff, **sem** checagem de plano; tenant derivado do token (policy de capability, `withSignatureToken`). Estados retornados como código: token inexistente → `NOT_FOUND` (`invalid`); já usado / `status!=pending` → `ALREADY_USED` (`used`); expirado → `EXPIRED` (`expired`). Consumo `consumeAndCapture`: `UPDATE … WHERE used_at IS NULL` atômico (uso único / corrida) grava captura 1:1 sob `withOrg(orgId)`.
- REST `POST /api/v1/pgr/[id]/signature` = 201, body só `ttlSeconds?` (`.strict()` → qualquer outro campo 422); `GET` = 200 estado derivado, sem token.

### Regras de negócio efetivas

- Consolidado agrega joins profundos escopados por org; riscos ordenados por `risk_level` desc, sem avaliação por último; read-only.
- PGR↔GES e Revisões isolados por `(org_id, pgr_id, …)` com UNIQUE; revisão registra nº (server-calculado)/data/notas — histórico append-only, autor no audit log.

### O que foi implementado (código como fonte)

- **Catálogo (#29)** — CRUD completo (`training-catalog.ts` repo + action + REST). `UNIQUE(org_id,
name)` → `DUPLICATE`. Exclusão defensiva: `SELECT ... FOR UPDATE` → conta dependentes
  (`records` + `requiredLinks`) → `EntityInUseError`/`IN_USE` (409) se houver; `RESTRICT` do banco
  (23503) é backstop convertido no mesmo erro. `GET /[id]/dependents` = contagem informativa sem lock.
- **Registro de realização (#30)** — `createTrainingRecord`: numa transação única valida
  funcionário e treinamento **dentro do tenant** (cross-tenant → `FK_NOT_FOUND`, pois a FK do banco
  não enxerga `org_id`), calcula `valid_until` no servidor via **D1 `computeValidUntil`** pela
  periodicidade vigente do catálogo, e persiste (D6 — mudar a periodicidade depois não move
  realizações passadas). `completedAt` validado por Zod: data-calendário e **não-futura** vs.
  `todayInSaoPaulo()`. Histórico por funcionário ordena `completed_at DESC, created_at DESC`.
- **Vencimento/reciclagem (#31, US3)** — `listTrainingExpiry`: **D5** (subquery `ROW_NUMBER() OVER
(PARTITION BY employee_id, training_id ORDER BY completed_at DESC)` → só `rn=1`), filtra
  `valid_until IS NOT NULL` (exclui `single`), classifica por **D2 `classifyTrainingStatus`**
  (janela `dueWithinDays` 30/60/90). Resumo `{expired, dueSoon}` (janela fixa 30d) p/ dashboard.
- **Obrigatórios por função (#28/#80, US4)** — `addRequiredTraining` **idempotente**
  (`onConflictDoNothing` sobre `UNIQUE(org, job_role, training)` → repetir devolve o vínculo
  existente, sem erro). `getEmployeeCompliance`: por obrigatório da função do funcionário, status do
  último registro (D5+D2, janela fixa 30d); sem registro → `missing`; registro `single` → `ok`;
  funcionário sem função ou função sem obrigatórios → lista vazia; funcionário inexistente/
  cross-tenant → `NOT_FOUND`. `listNonCompliance` = mesma regra sem filtro, devolve só `missing`/`expired`.

### Regras de negócio efetivas

- Periodicidade enum `annual/biennial/triennial/quinquennial/single`; `valid_until` =
  `completed_at` + {1,2,3,5} anos; **`single → null`** (nunca vence). Date-only UTC (29/02 rola p/
  01/03 em ano não-bissexto, determinístico).
- Status (D2, fronteiras **inclusivas**, fuso `America/Sao_Paulo`): `valid_until < hoje` → **vencido**;
  `valid_until <= hoje+janela` → **a vencer**; senão → **em dia**; `valid_until = null` → **em dia**.
- Obrigatórios por função: sem registro = **ausente** (não-conforme); registro vencido = não-conforme;
  `single` excluído do controle de vencimento (mas conta como conforme na conformidade).
- Resumo dashboard `{expired, dueSoon}` (janela 30d, sem cron/notificação).
- Certificado = `certificate_path text` (D4 — sem GED/upload).
- Isolamento em todas as tabelas; tenant da sessão, nunca do cliente. Papel `client` → `FORBIDDEN`.

### O que foi implementado (código como fonte)

- **OS (service-orders):** CRUD + itens de checklist na mesma transação (substituição transacional da coleção no update). Número sequencial por tenant `max(number)+1` (`nextServiceOrderNumber`) sob lock (`SELECT ... FOR UPDATE` na linha de `orgs`) + backstop `UNIQUE(org_id, number)`. `days_open` derivado (`computeDaysOpen`, nunca persistido). Itens têm `source_type` (`manual|risk|epi`, TEXT) com snapshot congelado (≤100 itens, descrição ≤500). Estados editáveis: `open`/`in_progress`; terminais `completed`/`cancelled` não retrocedem (`canTransitionServiceOrder`). Exclusão só em não-terminal (terminal → `IN_USE`).
- **Assinatura da OS:** `createServiceOrderSignatureRequestAction` (officeAction) → core monta payload no servidor (`buildServiceOrderDocumentTitle`) e cria `signature_request` (`target_type='service_order'`). Estado derivado `none|pending|signed|expired|cancelled` (`deriveServiceOrderSignatureState`); GET protegido nunca devolve token/URL/hash. - **Incidentes/Acidentes (accidents):** CRUD com enums fechados + campos CAT `cat_number`/`cat_issued_at` textuais/opcionais (registro interno, **sem S-2210/eSocial**). ### Regras de negócio efetivas

- OS: número sequencial único por tenant (lock + UNIQUE); concorrência no mesmo tenant → números consecutivos; tenants distintos podem repetir número. Itens ≤100/desc ≤500. Transições válidas apenas; terminal não retrocede. Assinada = imutável. Assinável só com itens + funcionário.
- Assinatura: token só hasheado, uso único (replay bloqueado), expirado/cancelado rejeitados, token inválido não revela existência da OS; payload mínimo (6 chaves, sem PII/ids internos) e congelado.
- Incidente: ciclo linear + cancelamento; conclusão exige justificativa e é bloqueada com plano ativo; CAT como texto; sem eSocial; sem coluna de fotos/arquivos.
- Plano: origem `risk|incident` validada na app; 5W2H obrigatório (5W+how); priority 1–3; overdue derivado; exclusão só planejado; terminal imutável; origem removida preserva histórico.
- Auditoria: kanban linear, conclusão com justificativa; 1 ativa por origem; sugestão IA premium com cota + fallback controlado.

### Regras de negócio efetivas (verificadas no código)

- **Plano** (`inspection-plans.ts`): `type` **vehicular|equipment** (`planTypeSchema` — segurança NÃO
  usa plano), `title` obrigatório. Itens = sub-tabela `inspection_plan_items` gravada na criação/edição;
  `order` = índice do array (`itemRows`); `updatePlan` **substitui todos** os itens (delete+insert).
  `ON DELETE CASCADE` plano→itens. `deletePlan` **não bloqueia** se em uso — `inspections.plan_id` é
  `ON DELETE SET NULL`, então excluir plano usado apenas anula a referência da inspeção (sem IN_USE).
- **Veículo** (`vehicles.ts`, `domains/inspections/vehicles.ts`): `plate` normalizada (uppercase, sem
  separadores) e validada **legado** `AAA0000` **ou Mercosul** `AAA0A00` (`plateSchema`); `UNIQUE(org_id,
plate)` → **DUPLICATE** (23505). `initialKm` int ≥0 (Zod + CHECK `initial_km >= 0`). `type` enum opcional.
  ⚠️ **`deleteVehicle` NÃO bloqueia veículo em uso** — sem checagem de dependentes; FK
  `inspections.vehicle_id` é `ON DELETE SET NULL`, logo a exclusão sucede (204) e anula o vínculo da
  inspeção. (Divergente da premissa "bloqueio ao excluir em uso".)
- **Inspeção veicular** (`vehicular-inspections.ts`): create exige veículo **e** plano do tenant com
  `plan.type = vehicular` (`assertVehicleAndPlan`); falha → repo retorna null → **FK_NOT_FOUND**
  (`ReferenceNotFoundError`). Status **`in_progress` já na criação** (não `pending`). `saveChecklist`
  (PUT) substitui respostas, **filtra `planItemId` que não pertence ao plano** (defesa contra id forjado),
  e marca **`completed`**. `UNIQUE(inspection_id, plan_item_id)`. Checklist tri-state: `value` true/false/null.
  **Não há** transição explícita para `cancelled` nem action de mudança de status isolada.
- **Inspeção de segurança** (`safety-inspections.ts`): livre (sem plano). `category` enum obrigatório,
  `companyId` opcional (asserção → **FK_NOT_FOUND** se cross-tenant), `planned` bool. Ocorrências
  (PUT `/occurrences`): `description` obrigatório + `severity` enum nullable; substitui todas e marca
  **`completed`**. Create → `in_progress`. Assinatura: `requestInspectionSignatureAction` gera pedido
  (token) via infra de assinatura; NOT_FOUND se inspeção não é do tenant.
- **Inspeção de equipamento** (`equipment-inspections.ts`): exige `equipmentCatalogId` do `epi_catalog`
  com **`type = machine`** + plano `type = equipment` (`assertEquipmentAndPlan`) → senão **FK_NOT_FOUND**;
  sem campos veiculares. Checklist idêntico (PUT, `completed`). Create → `in_progress`.
- **PT** (`work-permits.ts`): **`number` é texto obrigatório fornecido pelo usuário**, `UNIQUE(org_id,
number)` → **DUPLICATE** (não há geração sequencial automática — divergente da premissa "número
  sequencial por org"). `type` enum obrigatório; `status` default `draft`; `description` obrigatório;
  `validFrom`/`validUntil` (YYYY-MM-DD) com `validUntil >= validFrom` (refine Zod **e** CHECK
  `work_permits_valid_range_check`). `companyId` opcional asserido → **FK_NOT_FOUND** cross-tenant.
  Transições de status via **update do registro inteiro** (não action dedicada de transição).
- **Isolamento**: toda leitura/escrita `withOrg(tenantId)`; tenant da sessão (`officeAction`/
  `restHandler`→`requireOfficeStaff`), nunca do input. `client` → **FORBIDDEN**. Sem contexto de tenant
  → gate bloqueia; repo/RLS nunca vaza cross-tenant.

### Regras de negócio efetivas

- **Campanha status** (`STATUS_TRANSITIONS`): `draft→{active,archived}`, `active→{closed,archived}`, `closed→{active,archived}`, `archived→{}` (terminal). Mesmo→mesmo permitido.
- **Ativação** exige ≥1 pergunta (`canActivateCampaign`); ativar sem pergunta → `VALIDATION` ("Campanha sem perguntas não pode ser ativada").
- **Perguntas**: sub-entidade com `position` (append = max+1); `reorder` up/down por swap de position (borda = no-op); remover pergunta com respostas em campanha **ativa** → `IN_USE` (`EntityInUseError`).
- **Resposta pública anônima**: `resolvePublicCampaign` exige token válido **e** `status==="active"` **e** dentro do período (`startsAt<=hoje<=endsAt`, fuso SP). Token inválido → `kind:"invalid"` → REST/action `NOT_FOUND`; encerrada/fora do período → `kind:"not_open"` → `VALIDATION`. Cada submit cria **novo** `psychosocial_response` (token uuid próprio, não identifica); answers filtradas para `questionId` pertencente à campanha (ids forjados descartados). Não há bloqueio server-side de resposta dupla por participante — cada POST gera nova resposta anônima.
- **Stats/derivação isolados por tenant**: `getCampaignStats` só agrega respostas da campanha do `orgId`; `deriveRisks` — só perguntas `likert` com `average>=threshold(3)` viram fator, nível `classifyLevel` (≥4.5→4, ≥3.75→3, ≥3→2, senão 1); upsert por `(org,campaign,factor)` (re-derivação idempotente).
- **registerRiskInPgr**: cria `risks` (`agentType:"psychosocial"`, description=factor) no GES informado e vincula `riskId`; idempotente (se já vinculado, no-op retorna riskId); GES inexistente/cross-tenant → `FK_NOT_FOUND` (`ReferenceNotFoundError`).
- **conclude**: encerra campanha (`→closed`).
- **eSocial evento**: `createEvent` nasce **`pending`** (não draft — o enum tem `draft` mas geração já entra pending); geração valida input pelo schema do tipo e monta XML (sem envio). `generateS2240FromRiskAction` exige `noxiousAgentCode` no risco → senão `FK_NOT_FOUND`.
- **Lote**: `sendBatch` agrupa **só eventos `pending` do tenant** (filtro `inArray` + `status="pending"` + `orgId`); ids de outro tenant/não-pending são silenciosamente ignorados; nada elegível → `NOT_FOUND`. Gera `protocolNumber`, marca eventos `sent`. `queryBatchReturn` marca eventos `sent` do lote → `accepted` e lote → `processed` (simulado).
- **Isolamento**: todo acesso via `withOrg` + RLS backstop; público via `withPsychosocialToken` (tenant derivado do token, nunca do cliente). Papel `client` → `FORBIDDEN` no gate `requireOfficeStaff` (Server Actions/REST autenticadas).

### O que foi implementado (código como fonte)

- **Dashboard/KPIs** (`repositories/dashboard.ts` + `domains/platform/dashboard.ts`): read-model agregado escopado ao tenant. Toda query filtra `org_id` explicitamente **além** do backstop RLS via `withOrg`. KPIs: `companies`, `employees`, `workUnits`, `ges`, `risks`, `pgrs`. Distribuições `risksByAgentType` (group by `risks.agent_type`) e `actionPlansByLevel` (`control_measures` com `applicable=true`), com **zero-fill** por enum (`zeroFillCounts`) e `withBarPercents` (percentual relativo ao maior valor; série zerada → 0%). Bloco `pending`: `pgrsExpired` (`pgr.valid_until < hoje`), `controlsOverdue` (`control_measures` aplicável + `action_deadline < hoje`), `episLowStock` (`epi_stock.balance < min_quantity`), `episPendingReturn` (itens sem `returned_at` e entrega já não-`pending`), `trainingsExpired`/`trainingsDueSoon` (reusa `getTrainingDueSummary`). `hoje` = `todayInSaoPaulo()`.
- **Pendências** (`repositories/pending-items.ts`): top-5 (`CAP=5`) por grupo SÓ das pendências **sem tela dedicada** — `pgrsExpired`, `controlsOverdue`, `episLowStock` — cada item com `href` para a origem (`/pgr/[id]`, `/risks/[riskId]`, `/epi-stock`). Treinamentos/devoluções têm páginas próprias. Escopo `org_id` + `withOrg`.
- **Notificações** (`domains/platform/notifications.ts`): `buildNotifications(pending)` puro — um alerta-resumo por categoria com contagem > 0, linkando à origem, severidade `high` (PGR/controles/treinamentos vencidos) ou `medium` (EPI baixo/EPI a devolver/treino a vencer). **Sem persistência**; "lido" resolvido no cliente via localStorage (chave estável `key`). Sem tabela nem e-mail.
- **Agenda** (`schema/schedule-events.ts` + `domains/platform/scheduling.ts` + actions/repo): CRUD de `schedule_events` (enum `inspection|training|exam|document_expiry|other`), campos `title`, `eventDate` (`AAAA-MM-DD`), `description?`, `referenceUrl?`. Filtros de lista: `eventType` + janela `from`/`to`. Isolamento por tenant (RLS `schedule_events_isolation` + `withOrg`). Actions `officeAction` com `audit:true` em create/update/delete; NOT_FOUND para id inexistente/cross-tenant.
- **Relatórios** (`domains/platform/reports.ts` + `reports-core.ts` + `api/v1/reports/[type]`): `organization-summary` disponível → HTML montado no servidor (após gate de tenant) → Gotenberg → PDF (`application/pdf`, `Content-Disposition attachment`). Tipos `esocial-events`/`onboarding-manual` marcados `available:false`. Handler dedicado (não `restHandler`, resposta binária): `requireOfficeStaff` → tipo inexistente `404 NOT_FOUND`; indisponível `503 REPORT_UNAVAILABLE`; `FORBIDDEN` 403.
- **Perfil** (`domains/platform/profile.ts` + `profile-core.ts`): edita só campos app-managed (`phone`, `cpf` opcional validado, `jobTitle`); nome/e-mail/foto são **read-only** (Clerk é a fonte da verdade — **senha via Clerk**). `officeAction` `audit:true` no update.
- **Equipe/multiusuário** (`team-core.ts`): `listTeam` (paginado, busca). Escritas (`invite`/`updateRole`/`remove`) exigem **`ctx.role === "owner"`** (`requireOwner` → `FORBIDDEN`) **e** plano Pro com Clerk org (`requireClerkBackedTeam`: `isTeamManagementAvailable(plan)`==pro + `org.clerkOrgId`, senão `FORBIDDEN` "disponível apenas no plano Pro"). Proteções: não rebaixar/remover o **último owner** (`countOwnersByOrg <= 1` → `FORBIDDEN`); não remover a si mesmo. Convite/alteração/remoção delegam ao Clerk. NOT_FOUND para membership inexistente.
- **Billing/Trial Stripe** (`billing-core.ts` + `orgs.ts` + webhook): `startProCheckout` só `owner` (senão FORBIDDEN) → Checkout Pro com `TRIAL_DAYS=7`; sem URL → `BillingUnavailable`. Webhook público valida **assinatura HMAC** (`stripe-signature`; sem/ inválida → `400`, corpo lido cru). `handleStripeEvent`: `checkout.session.completed` → plano `pro` + grava customer/subscription; `customer.subscription.created/updated/deleted` → `planFromSubscriptionStatus` (`active`|`trialing` → `pro`, senão `free`) + `trialEndsAt`. Stripe é a fonte da verdade; `orgs.plan` é espelho (`check` `in ('free','pro')`). Resolução do org por metadata `orgId` → `client_reference_id` → `stripeCustomerId`.
- **Onboarding** (`domains/platform/onboarding.ts` + action): progresso **derivado** dos KPIs (sem flag persistida) — 5 passos na ordem da cadeia (empresa→funcionário→GES→risco→PGR), `done = kpis[step.key] > 0`; retorna `completed`/`total`/`percent`/`allDone`.
- **Admin global** (`require-master.ts` + `master-action.ts` + `repositories/admin.ts` + actions/platform/admin.ts): gate `requireMaster` pela flag **global `users.is_master`** (NÃO papel de tenant; cross-tenant). `masterAction` espelha `officeAction` com gate global. Operações: `listMasters`, `aiUsageByOrg` (agregação de `ai_usage_events` por org, ordenada desc — monitoramento de uso de IA), `promoteMasterByEmail`, `demoteMaster` (proteção: `countMasters <= 1` → FORBIDDEN, não remove o último master). Repo usa service client (bypassa RLS) — permitido só sob o gate master.

### Regras de negócio efetivas

- KPIs e todas as agregações **escopados por org** (filtro `org_id` explícito + RLS `withOrg`); tenant sempre da sessão, nunca de input do cliente.
- Pendências agrupadas por tipo, top-5 com link à origem; notificações **derivadas** das pendências (contagem>0), "lido" client-side; badge = nº de notificações.
- Agenda: CRUD isolado por tenant + vencimentos automáticos (`document_expiry` e demais tipos) aparecem na listagem/filtro.
- Relatórios via Gotenberg escopados ao tenant; só tipos `available` geram PDF (senão 503).
- Perfil: senha e identidade via Clerk; app edita só phone/cpf/jobTitle.
- Equipe: convite/alteração/remoção de papel **só admin (owner) e só plano Pro**; senão FORBIDDEN. Free não tem multiusuário.
- Billing: trial 7 dias, plano free/pro; webhook Stripe (assinatura verificada) atualiza plano/expiração; `orgs.plan` é espelho.
- Onboarding: progresso derivado por org, sem persistência.
- Admin global: só superadmin (`is_master`), não escopado por org mas protegido pelo gate master; senão FORBIDDEN.

## 15. Documentos, Pastas e Jobs — Modelo de dados (#33)

`Specs:` `.specs/023-documents-data-model/` (spec/plan/data-model/research/contracts/quickstart) · `Migrations:` `0025_documents_data_model` (`src/shared/db/migrations/0025_documents_data_model.sql`) · `PR:` #176 · `Status:` **modelagem pura** (schema + migration + RLS + testes; SEM UI/CRUD)

> ⚠️ Escopo: esta fatia entrega apenas o **modelo de dados**. Os **fluxos** (CRUD do GED, geração de URL assinada de download, geração de PDF, worker de jobs) **NÃO foram implementados** — permanecem nas issues abertas **#34–#40, #88**. O QA abaixo é de **modelo/constraints/RLS**, não E2E de UI.

### O que foi implementado (código como fonte)

- **Schema** — `src/shared/db/schema/documents.ts` (`folders`, `documents`, enum `document_status`) e `src/shared/db/schema/jobs.ts` (`jobs`, enums `job_type`, `job_status`).
- **Enums**: `document_status` = `generating|ready` (default `ready`); `job_type` = `pdf_batch`; `job_status` = `pending|processing|done|failed` (default `pending`).
- **Domínio** — `src/shared/domains/documents/validity.ts`: `classifyDocumentValidity(validUntil, {today, dueWindowDays})` → `ok|due_soon|expired|no_expiry` (derivada na leitura, date-only, fronteiras inclusivas; espelho de `classifyTrainingStatus` da 017) + `documentRelatedEntityTypeSchema` (`z.enum(["pgr"])`, conjunto fechado FR-005).
- **Testes** — integração (Postgres efêmero): `documents-model.test.ts`, `documents-isolation.test.ts`, `folders-model.test.ts`, `jobs-claim.test.ts`; unit: `unit/domains/documents/validity.test.ts`.

### Regras de negócio efetivas

- **3 tabelas** (`folders`, `documents`, `jobs`), cada uma com `org_id text NOT NULL → orgs.id ON DELETE CASCADE`, índice por `org_id`, `enableRLS()` e policy `*_isolation` (`FOR ALL` ao `app_runtime`, `USING`/`WITH CHECK` = `org_id = current_setting('app.current_org', true)`).
- **folders**: `parent_id uuid` auto-referência (raiz = NULL, `ON DELETE RESTRICT`); unicidade de irmã `uq_folders_org_parent_name` sobre `(org_id, parent_id, name)` com **NULLS NOT DISTINCT** → cobre inclusive duas raízes de mesmo nome.
- **documents**: `folder_id → folders ON DELETE RESTRICT` (nullable = raiz do GED); `document_group_id uuid NOT NULL` (1 linha por versão); `version integer default 1`; **`uq_documents_org_group_version`** sobre `(org_id, document_group_id, version)`; `doc_type text NOT NULL` (texto livre); `valid_until date` **nullable** (validade derivada na leitura, sem coluna de status); `storage_path text NOT NULL`, `size_bytes bigint NOT NULL`.
  - CHECKs: `documents_version_check` (`version >= 1`), `documents_size_bytes_check` (`size_bytes >= 0`), `documents_related_entity_check` (`(related_entity_type is null) = (related_entity_id is null)` — vínculo completo-ou-vazio).
  - **Vínculo polimórfico** `related_entity_type/related_entity_id` **sem FK** (índice parcial `idx_documents_related_entity` onde `related_entity_type is not null`) — documento sobrevive ao sumiço da entidade vinculada.
- **jobs**: fila com claim atômico `FOR UPDATE SKIP LOCKED` + `locked_at` (stale claim); `payload jsonb NOT NULL default '{}'`, `result jsonb`, `attempts integer default 0` (`jobs_attempts_check attempts >= 0`); índice `idx_jobs_status_created_at`. Worker é da #39 — nesta fatia só o modelo/contrato SQL.
- **Cascata**: CASCADE apenas em `org → tabelas`; RESTRICT em `folders→folders` e `documents→folders` (não apaga pasta com filhos/documentos).
